# 交叉评审意见（M3 → M1 / M2）

> 对应协作机制：**10-13 交叉评审，每人审另一个人的交付物，写 3 条反对意见。**
> 本文件是 M3 对 M1、M2 交付物的评审意见。每条都附**可复核的依据**（文件行号或一条命令），
> 不含"我觉得"式的意见。
>
> 评审原则：**对别人严，对自己也一样严**——最后一节是 M3 接受反向意见的记录。

## 一、对 M1 交付物的三条反对意见

### 反对 1（最重要）：Skill 里完全没有尺度检验，智能体会漏掉判别力最高的一道门

**依据**：

    > python -c "print(open('skills/formula-discovery-loop/SKILL.md',encoding='utf-8').read().count('scale'))"
    0

`skills/formula-discovery-loop/SKILL.md` 全文 **0 次**提到尺度检验。而它同时写着：

- 第 27 行（硬约束第 2 条）："**禁止跳过任何一项检验**。三项都必须跑。"
- 第 14 行与第 33—44 行（工具接口速查）：只给了 `verify` / `batch` / `validate-tasks` 三条命令。
- 第 3 行的 `description`：只写"留出集/外推区/量纲三重检验"。

**后果**：Agent 按 Skill 执行时，不会知道尺度判据的存在，更不会在失败时去读它的理由。
而实测数据显示尺度判据恰恰是判别力最高的一道（22/22），失败理由也最有指导性
（"曲线对振幅完全平坦，说明漏掉了这个自变量"）。

**建议**（M1 只需改文档，不需要改代码）：

1. 第 3 行 description 改为"四重检验：留出集 / 外推区 / 量纲 / 尺度"；
2. 第 27 行改为"四项都必须跑"；
3. 工具速查补一条：
   `python -m formula_agh.scale_checks --task tasks/<id> --formula "..." --params G=6.674e-11 --run-id <id>`；
4. 第 16—21 行的"显式处理失败"补一类：`scale-*` 失败 → "单位可能对、形状不对，**必须换函数族**"。

### 反对 2：演示脚本 `demo_agent.py` 不含尺度检验，视频的自我否定片段与轨迹对不上

**依据**：

    > grep -c "scale" examples/demo_agent.py
    0

`examples/demo_agent.py` 是"自主闭环演示（无需模型账号）"的脚本，
它产出的 `runs/demo-gravitation/` 与 `runs/demo-self-negation/` 会被用来录制视频。

**后果**：视频脚本 2:30—3:05 的旁白是"物理判据指出——距离加倍，引力应该变成四分之一"，
但按当前脚本跑出来的轨迹里**根本没有 scale 判据这一项**。录屏与旁白对不上，
这在评审看来比不讲更糟。

**建议**：在 `demo_agent.py` 的判定逻辑里显式调用尺度检验（或直接把
`verify_formula(..., scale_check=True)` 打开），让轨迹里出现 `scale-scaling-r` 这一项。
M3 已备好可直接录屏的命令与真实输出，见 `evidence/video/seg-self-negation.log.txt`。

### 反对 3：`harness/` 下缺少尺度检验的包装脚本

**依据**：`harness/` 目前只有 `run_verify.cmd`、`run_batch.cmd`、`run_validate_tasks.cmd`。

**后果**：视频脚本第 5 条接入步骤让智能体"用命令工具执行 `harness\run_verify.cmd ...`"，
但尺度检验没有对应脚本，AGH 侧要调用就得手写长命令，容易输错参数
（例如漏掉 `--params G=6.674e-11` 会让自由参数变成未知符号，直接判表达式失败）。

**建议**：补一个 `harness\run_scale_check.cmd`，与现有三个脚本同构。

## 二、对 M2 交付物的三条反对意见

### 反对 1：`docs/运行与验证.md` 里的命令已被证伪，且测试数字三处互相矛盾

**依据**：

- 第 33 行：`python -m formula_agh verify --task tasks/mech-gravity ...`
- 第 85 行：`harness\run_verify.cmd tasks\mech-gravity "G*m1*m2/r**2" G`

**`tasks/mech-gravity` 这个目录不存在**——实际任务名一律是 `phys-*`。
任何照抄文档复现的人，第一步就会失败。

同一份文档里还有三个互相矛盾且已过时的测试数字：

| 行号 | 原文 | 当前实际 |
|---|---|---|
| 16 | "10 项测试全部通过" | 50 项 |
| 18 | "10 passed / 0 failed" | 50 passed / 0 failed |
| 90 | "self-test 12 passed / 0 failed" | 50 |
| 92 | "wrong variants 21 / 21 rejected" | 22 / 22 |

**后果**：复现者会认为文档不可信，进而怀疑结论。这是最容易被评审抓到的低级问题。

**建议**：把文档里所有命令改成当前可执行的形式（至少先跑一遍），
并把测试数字换成一句"运行 `python run_tests.py` 查看当前数字"，避免再次写死。

### 反对 2：`verify_formula` 的 `scale_check` 默认值是 `False`，直接调用者会静默少一道门

**依据**：`src/formula_agh/verify.py` 第 452—461 行

    def verify_formula(formula, columns, meta, parameters=None, initial=None,
                       holdout_threshold=0.08, extrapolation_threshold=0.15,
                       ..., dimension_check=True, scale_check=False, ...)

注释说明了理由（"纯引擎原语，不读配置文件"），这个取舍本身是合理的。
但 `dimension_check` 默认 `True` 而 `scale_check` 默认 `False`，
两者不对称，调用者不容易察觉。

**而且这个坑我自己踩了**：M3 的 `examples/discrimination_report.py` 第一版直接调用
`verify_formula` 而不传 `scale_check`，得到的结论是"三重验证单独拦下 22/22，
尺度检验增量为 0"，**差一点就得出了一个对我们自己不利的错误结论**。
发现后已改为从 `config/agent.yaml` 取开关并重跑。

**建议**（三选一，都比现状好）：

1. 在返回的 `VerifyReport` 里加一个字段 `enabled_checks`，明确写出"本次启用了哪几道门"；
2. 在 `rounds_hint` 里加一句"本次未启用尺度检验"；
3. 至少在 `verify_settings()` 的返回里加一个 `warning` 字段提示默认值不对称。

### 反对 3：`reproduce.py` 的复现范围不含 M3 的三套验收脚本

**依据**：`reproduce.py` 第 43—45 行

    EXCLUDE_DIRS = {"runs", "evidence", "recheck", "sealed", "superseded", ...}

排除 `evidence`（生成物）是合理的。但复现流程本身没有覆盖：

- `examples/scale_check_all.py`（22/22 与 0/22 的双向判别力）
- `examples/dimension_acceptance.py`（量纲门覆盖率与互补性）
- `examples/negative_control.py`（80 次攻击零编造）

**后果**：一键复现"成功"只证明三重验证可复现，**不代表整条证据链可复现**。
而这三套脚本恰恰是"验证严谨性"与"异常处理"两项的主要证据来源。

**建议**：把三个脚本加进 `reproduce.py` 的步骤列表，把它们的关键输出
（`22/22`、`0/22`、`pass 13 / skip 9`、`accepted 0`）写进
`expected/reproduction_baseline.json` 做指纹比对。三个脚本都是零依赖、确定性的，
不会给复现引入不稳定性。

M3 在 `evidence/交叉评审发现.md` 的"发现 3"曾指出：
`config/agent.yaml` 声明了 `scale_check: true` 但没有消费方。

**这条已由 M2 解决**。复查证据：

- `src/formula_agh/verify.py` 第 413 行新增 `_scale_check_results()`，第 564—565 行按开关追加；
- `src/formula_agh/cli.py` 第 187、247 行与 `recheck.py` 第 169 行都已从配置传入开关；
- M3 的端到端复验（走 CLI 同一条代码路径）：

      四道门端到端：参考式接纳 22 / 22

M3 保留这条记录而不是删掉，理由与保留失败案例相同：
**评审需要看到"意见被提出、被处理、被复验"的完整过程，而不是一个干净的结论。**

## 四、M3 接受反向意见的记录（对自己用同一把尺子）

| 问题 | 谁发现 | 后果 | 处置 |
|---|---|---|---|
| `discrimination_report.py` 未传 `scale_check`，把"三重验证单独把关"当成了完整流水线 | M3 自查（写反对 2 时发现） | 差点得出"尺度检验增量为 0"的错误结论 | 已改为从配置取开关并重跑，`evidence/discrimination.json` 全量更新 |
| 尺度检验的极限判据最初用最粗探测点统一归一化 | 自己的回归测试 | 恒定相对偏差会伪装成收敛，放过错误公式 `d*sin(theta2)*n` | 改为逐探测点归一化，并加了专门的回归测试 |
| 单调性判据最初用等距采样 | 金标准自检 | `q*B/m` 在高质量端看起来像常数，正确公式被误判 | 跨度 ≥10 倍时自动改等比采样 |
| 标度判据最初不支持缩放自由参数 | 金标准自检 | 参考式 `(A-B)/h` 被误判 | 允许探测点覆盖自由参数取值 |
| 同类判据重名 | 自查 | `checks/<name>.json` 互相覆盖，证据丢失 | 检验名去重 + 回归测试 |
| 数据卡初稿的 `%%` 渲染错误、"表中每一条来源链接都可点击"但表里没有链接 | 自查 | 文档与事实不符 | 已修正并把来源列加进表内 |

前四条都是**先出现错误结论、再被测试抓住**的。留在这里是为了说明：
本队的评审标准对三个人是一致的，M3 的判据本身也要被判据检验。
