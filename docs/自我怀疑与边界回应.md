# M2 怀疑清单与回应

> 分工文档给 M2 列了 5 条必须主动攻击自己的问题。这一份逐条给结论、给证据、给复现命令。
> 原则：**能证伪的就写证伪，不能识别的就写不能识别**，不写成"基本没问题"。

## 怀疑清单第 1 条：留出集是不是真的没被智能体看到？

**结论：改造前只是口头保证，现在做到了文件系统级别的隔离。**

改造前：留出点与训练点同处一个 `data.csv` 里，"没被看到"完全依赖智能体自觉
不越界去拟合全部数据——这不是工程保证，是纪律要求。

现在分三层：

1. **物理分离**：`sealed/<task>/holdout.csv` 与 `sealed/<task>/extrapolation.csv`
   被写到 `tasks/` **之外**（与 `reference/` 同级）。智能体遍历任务目录时读不到。
   智能体可见的工作集是 `tasks/<task>/data_train.csv`，只含训练点。
2. **划分描述不含行号**：`tasks/<task>/split.json` 只有规则、计数、支撑域与集合指纹，
   没有任何行号数组。`formula_agh.split.assert_no_indices()` 会主动扫描并抛错。
3. **标准答案文件扫描**：任务目录内出现 `reference/answer/ground/solution/truth/label/golden`
   九类文件名，契约校验直接报 error。

复现：

    python -m formula_agh validate-tasks --tasks tasks --reference reference --require-split --strict
    python -m formula_agh split --tasks tasks --check

证据：`evidence/adversarial/report.md` 的"留出集隔离"用例。

**留下的边界**：封印只防"按目录遍历读文件"。智能体如果拿到宿主机绝对路径仍然能读，
这一点靠 AGH 的工作目录与沙箱策略约束，不在这份脚本的能力范围内——如实标注。

## 怀疑清单第 2 条：外推区是不是真的在支撑域之外？

**结论：是，22 个任务逐点核对通过。**

对每个任务：

* 主自变量 = 极差最大的自变量；按它排序后取最小端与最大端各 7.5%，合计 15% 作外推区；
* 支撑域 `[support_lo, support_hi]` **只由训练点**决定（不是由全量数据决定）。

实测：

    外推点严格位于训练支撑域之外：1320 / 1320  （100%）
    留出点严格位于训练支撑域之内：1760 / 1760  （100%）
    越界任务：无

复现：`python examples/adversarial_suite.py` -> "外推区严格位于训练支撑域之外" 用例。

**留下的边界**：本项目数据是按声明区间均匀采样生成的，两端并不稀疏，
所以外推区比真实实验数据要"温和"。这是任务集的已知局限，已写入数据卡。

## 怀疑清单第 3 条：量纲检验会不会被绕过？

**结论：改造前被绕过了 8 次，现在覆盖率 100%。这是本次审查最严重的一处发现。**

`units.py` 原来只做精确字符串查表。任务集里用到的
`m^3`、`T`、`F/m`、`H/m`、`ohm`、`m^2` 六个单位不在表内，
于是 `_check_dimension` 走"未知单位 -> 跳过检验"分支并**返回 passed=True**。

也就是说：22 个任务里有 **8 个**的量纲门是敞开的，而日志上看起来一切正常。

修法：保留查表快路径，落空时按复合单位文法解析
（`a*b`、`a/b`、`a^N`、括号），并补齐导出单位
（特斯拉、韦伯、法拉、亨利、欧姆、西门子）。

验证：`1/sqrt(eps*mu)` 在 `eps=F/m, mu=H/m` 下推出 `L·T^-1`，与 `m/s` 严格相等。
修复前后覆盖率对比与逐任务明细写在 `evidence/adversarial/report.md`。

**留下的边界**：单位表仍未收录的冷门单位会让该任务的量纲检验降级。
降级时判定结果是 `passed=True` 但 reason 明确写"跳过量纲检验"，
契约校验也会同时给一条 warn。也就是说**降级不会静默**，但确实是降级。

## 怀疑清单第 4 条：换种子结论会不会翻？

**结论：换判据前会翻，换判据后不翻。**

这是攻击判据本身最有效的一招。做法：把数据划分与拟合的种子换成
20261008 / 1 / 7 / 12345 / 99991 五个值，重跑 22 条金标准。

* 用旧口径 `RMSE / 中位|y|`：**`phys-cyclotron` 翻转**
  （留出集误差在 0.015 ~ 0.088 之间跳，阈值 0.05 正好落在中间）。
  根因是 y = qB/m 跨 17 倍动态范围，全局 RMSE 被少数大 |y| 点主导，
  而留出集是中间区域随机抽取的——换一组随机点就换一个结论。
* 用现口径 `median(相对误差)`：**翻转 0 / 22 条**。

复现：`python examples/adversarial_suite.py` -> "结论对随机种子的稳定性" 用例。

**留下的边界**：种子只影响划分与多起点搜索顺序，不影响判据定义。
如果判据本身依赖某个特定划分，这个实验会立刻暴露它——这正是它存在的意义。

## 怀疑清单第 5 条：负对照时会不会编造公式？

**结论：验证引擎这一侧不会，且是被主动检验的。**

做法：把 4 个任务的 y 整体换成标准正态噪声，把**正确答案**原样送进引擎。

    phys-ohm          I*R            -> rejected
    phys-weight       m*g            -> rejected
    phys-gravitation  G*m1*m2/r**2   -> rejected
    phys-spring-energy k*x**2/2      -> rejected

正确行为是报告"未发现稳定公式"。引擎做到了。

**必须说清楚的一点**：这只证明了**验证引擎**在负对照下不会放行。
"智能体在负对照下会不会硬编一个公式出来交差"是智能体侧的行为，
由 AGH Skill 硬约束第 5 条约束，但需要 M1 用真实会话记录来证明。
我们已经把负对照任务（`negative-control-*`）和判定脚本准备好了，
M1 跑完把会话导出放进 `evidence/negative-control/` 即可闭环。
**在那之前，这条只能写到"引擎侧已验证"，不能写成"系统不会编造"。**
