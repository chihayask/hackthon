## 反对意见 1：演示脚本的假设是人手写的，但它在证据包里和真实运行长得一模一样

**现象**

* `examples/demo_agent.py` 默认模式下，每一条「假设」都写死在脚本的 `STRATEGIES` 字典里，
  第 N 轮提什么由人预先排好；它调用的是真实验证引擎，但**假设不是模型提出的**。
* 它的产出写进 `runs/demo-*/`，再被归档进 `evidence/runs/`，与真实运行混在一起。
* 唯一的区分是 `run.json` 里一句 `notes: "自主闭环演示"`。
* 更糟的一例：`runs/demo-video-self-negation-01/run.json` 的 `notes` 是**空字符串**。

**为什么严重**

赛事对「AGH 与模型执行闭环」的要求原文是：完整运行轨迹日志，**证明全程零人工干预**。
把一个人工排好剧本的固定装置当作自主闭环证据提交，性质上属于把演示当实验结果。
这一条若被评委发现，损失的不是这一项的分数，是整个证据包的可信度。

**复现**

    python -c "import json;print(json.load(open('runs/demo-video-self-negation-01/run.json',encoding='utf-8')))"

**处置（M2 已改，请 M1 复核）**

* `src/formula_agh/evidence.py`：新增**必填**的 `hypothesis_source` 字段与词表，取值包括
  `agh-llm` / `human-authored-fixture` / `reference` / `fixture-variant` / `fixture-experiment` /
  `cli` / `unclassified`。未知取值直接抛错，不给含糊空间。
* `examples/demo_agent.py`：默认模式标 `human-authored-fixture`，`--llm` 模式标 `agh-llm`，
  notes 里写明「不得用于支撑智能体自主发现的结论」。
* `src/scoring/compare.py`：对照表第三层只统计 `agh-llm` 的运行；人工固定装置单独成层。
* `src/formula_agh/archive.py`：归档索引按来源分组统计，并列出所有 `unclassified` 的运行。

**这条目前仍有一个空洞，需要 M1 填**：`evidence/runs/` 里此刻没有任何一条 `agh-llm` 运行。
也就是说对照表的「智能体发现」层现在是空的——这不是缺陷，是事实，但必须让评委看到我们知道自己缺什么。

## 反对意见 2：演示轨迹引用的阈值与口径已经作废，而视频脚本正要引用它

**现象**

重跑之前，轨迹里写的是：

    runs/demo-gravitation/trajectory.jsonl
      round 4 holdout -> 留出集归一化误差 0.0069（阈值 0.0800）
    runs/demo-self-negation/trajectory.jsonl
      round 1 holdout -> 留出集归一化误差 0.1228（阈值 0.0800）

三处都对不上现行配置：口径是旧的 `归一化误差`（RMSE/std(y)），阈值是引擎默认的 `0.0800`，
而 `config/agent.yaml` 生效值是 `relative_error_median` 与 `0.02`。

**为什么严重**

`04_视频脚本与路演提纲` 的 2:10—2:45 是全片最重要的一段：智能体自己否决自己，那一段要展示的正是这些数字。
评审照着视频里的数字用当前配置复算，会得到另一个结果——这会直接摧毁「可复现」这条卖点。
M3 的发现 1 说的就是这件事，但只改了文档、没有重跑轨迹；而视频要的是**屏幕上的真实数字**，不是文档里的更正说明。

**根因（两层，都在 M1 的脚本里）**

1. `demo_agent.py` 调用 `verify_formula(...)` 时**没有传任何阈值与开关**，于是走引擎默认值。
   这正是「判据被静默降级」：入口不同、结论不同。
2. `trajectory.jsonl` 是用 `open(..., "a")` **追加**写的。同一个 run_id 跑第二遍，
   文件里会出现两套 `round 1..4`，而 `run.json` 只有一份——那份轨迹已经不代表任何一次真实运行。

**复现**

    python examples/demo_agent.py --task phys-pendulum-exact --run-id demo-self-negation
    python -c "print(sum(1 for _ in open('runs/demo-self-negation/trajectory.jsonl',encoding='utf-8')))"

**处置（M2 已改，请 M1 复核）**

* `demo_agent.py` 引入 `verify_settings()`，把阈值、比例、种子、两个开关、拟合门槛全部显式传入；
  并把轨迹由「追加」改为「运行开始先删除旧文件」。
* 重跑后的轨迹（各 4 轮，不再重复）：

      demo-self-negation  round 1  2*pi*sqrt(L/g)   rejected  failed=[holdout, scale-monotonic-theta0]
      demo-self-negation  round 4  精确式             accepted  failed=[]
      demo-gravitation    rounds 1-3 全部被否决，round 4 恢复平方反比律，G = 6.66187e-11

* 建议视频直接引用 `scale-monotonic-theta0` 那一行：它不依赖任何阈值，换口径也不会翻。
* `tests/test_m2_contract.py::test_every_entry_point_passes_all_switches` 已把 `demo_agent.py` 纳入接线锁，
  以后谁再漏传阈值，测试会红。

## 反对意见 3：该进配置的没进，进了配置的没人读

**现象 A：配置里声明的两条纪律没有任何代码读它**

`config/agent.yaml` 写着 `max_rounds: 6` 与 `max_rejected_before_restart: 3`；
`skills/formula-discovery-loop/SKILL.md` 硬约束第 4 条也写着
「禁止在同一函数形式上反复微调参数来刷过阈值。连续 3 次否决后必须更换函数族。」

但全仓库检索这两个键，只命中 `settings.py` 里的默认值表——**没有任何逻辑读取、没有测试覆盖**。
它现在是一条只写在纸上的纪律。

**现象 B：真正影响判定的阈值却硬编码在代码里**

`src/formula_agh/verify.py` 的拟合粗筛 `if rms > 0.5: raise VerifyError(不收敛)`。
这个 0.5 决定了一个候选是「拟合不出来」还是「进入留出集与外推区」，对判定结果有实质影响
——而它此前不在 `config/agent.yaml` 里，也没有出现在证据里。

**为什么严重**

* 纪律没有机器判据，等于没有纪律。评委问「怎么保证智能体没有连续微调参数」时，我们只能回答「Skill 里写了」。
* 阈值没进配置，等于「阈值统一在 config/agent.yaml」这句话不成立；而这句话正是我们用来回答
  「你们有没有为了通过而放宽阈值」的答案。

**处置**

* 现象 B 已由 M2 修完：`config/agent.yaml` 新增 `verify.max_fit_residual: 0.5`（注释写明它用的是已弃用口径、为什么保留）；
  `verify_formula` 接受 `fit_max_residual`，六个入口全部显式传入并写进证据；
  `fit` 检验的 metrics 现在同时记录训练集的多种口径残差，评审可以自己判断这道粗筛松紧是否合适；
  新增测试 `test_fit_threshold_comes_from_config_not_hardcoded`。
* 现象 A 属于智能体循环（M1），M2 给建议而不是代做：把「连续 3 次否决必须换函数族」做成对
  `runs/<id>/trajectory.jsonl` 的**机器检查**（每条记录已有 formula 与 verdict，
  判定「是否同一函数族」「是否只改了参数」是可计算的）。这样「纪律」也成为可验收项，
  与「对不对由机器判定」是同一个思路。如果 M1 同意，M2 可以在 10-14 之前补上这个检查器。

## 附二：一条会读反的输出（M3 的脚本，已改）

`examples/scale_check_all.py --variants` 原来打印：

    错误候选式被尺度检验否决: 0 / 22
    （期望值 = 0，即全部被否决）

这里的数字其实是「**通过**的条数」（`ok` 变量），标题却写成「被否决」。
字面意思是「一条都没被否决」，与实际（22 条全部被否决）正好相反，终端扫一眼或截图放进 PPT 都会读反。已改为：

    错误候选式通过尺度检验（越少越好，期望 0）: 0 / 22
    即被尺度检验否决: 22 / 22

## 附四：方案 A 的连带影响，以及它是怎么被抓出来的（M2 自我批评）

把尺度检验并进 `verify_formula` 之后，`examples/discrimination_report.py` 里的
`_as_report()` 仍然把 `record['scale']` 追加进 `checks[]`——而 `triple['checks']` 此时**已经含有同名项**。

后果不是报错，而是**静默的证据污染**：

* `result.json` 里出现 14 条检验，其中 5 个名字各出现两次；
* `checks/<name>.json` 每个名字只能有一个文件，于是后写的那份把先写的覆盖掉；
* 两份同名检验用的是**不同的参数取值**（一份用拟合值，一份用规格里的标称物理常数），
  数值因此对不上（实测相对差 1.8e-3）；
* 评审如果同时看 `result.json` 与 `checks/`，会看到两份互相矛盾的结果。

**抓到它的正是 M2 自己写的 `recheck`**：它把 `recheck/discrim-ref-phys-gravitation` 等 3 条运行
标成 `stale-metrics`（"判定可复现，但指标数值对不上"）。
这条状态是上一轮刚加的——加它的理由当时是"防止引用旧口径的数字"，
没想到第一个抓住的是**自己刚引入的集成缺陷**。

处置（两处，缺一不可）：

1. `_as_report()` 跳过重名项；`record['scale']` 段保留，因为它是"用标称物理常数做的受控对照"，另有价值。
2. `evidence.write_evidence()` 增加重名守卫：一旦报告里出现重名检验，
   写出 `checks/_duplicate_check_names.json` 并在 `run.json.duplicate_check_names` 里列出。
   证据里出现两份同名但取值不同的结果，从此不会是静默发生的。

修完复测：`discrim-ref-*` 的检验数从 14 回到 9，`duplicate_names` 为空，`recheck` 的 stale 计数归零。

## 附三：我认为值得写进最终文档的一条方法论

这次交叉评审里，M3 找出的三个问题、M2 找出的七个问题，**没有一个是「公式算错了」**。
全部是判据本身、证据本身，或者「声明与实现不一致」。

这恰好是本项目最该讲的一件事：一个验证系统的可靠性，不取决于它拒绝了多少公式，
而取决于它有没有能力拒绝**自己**。
